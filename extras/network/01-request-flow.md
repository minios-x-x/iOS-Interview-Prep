# URLSession 요청은 어떻게 서버까지 갈까 (1/4)

`URLSession`으로 API를 호출하는 건 익숙한 일이다. 그런데 "이 한 줄을 실행하면 네트워크에서는 무슨 일이 일어나나"라고 물으면 대답이 막힌다. 네트워크를 처음부터 다시 공부하면서 정리한 내용을 세 편으로 나눠 남긴다.

| 편 | 주제 |
|---|---|
| 1 | 요청이 서버까지 가는 길과 계층 (이 글) |
| 2 | HTTPS는 무엇을 어떻게 지켜 줄까: TLS, 인증서, handshake |
| 3 | IP 주소, IPv4와 IPv6, 네트워크 전환 |

## 1. 한 줄의 코드에서 시작한다

```swift
let (data, response) = try await URLSession.shared.data(
    from: URL(string: "https://api.example.com/users")!
)
```

처음 연결하는 서버라면 대략 이런 순서로 일이 일어난다(HTTP/1.1과 HTTP/2 기준).

```
DNS 조회    api.example.com의 IP 주소를 알아낸다
TCP 연결    그 주소의 서버와 연결을 맺는다
TLS         상대를 확인하고 암호화를 준비한다
HTTP        요청을 보내고 응답을 받는다
```

순서를 이해하려면 먼저 몇 가지 개념이 필요하다.

## 2. 먼저 알아야 할 것

### 2-1. 클라이언트와 서버

**클라이언트**는 요청하는 쪽(아이폰의 앱), **서버**는 요청을 기다렸다가 응답하는 쪽이다. 서버는 특별한 물건이 아니라 요청을 받는 프로그램이 켜져 있는 컴퓨터다.

### 2-2. IP 주소와 포트

- **IP 주소**: 네트워크에서 어느 컴퓨터인지 찾는 주소다. `203.0.113.10`처럼 생겼다.
- **포트**: 그 컴퓨터의 어느 프로그램에게 줄지 정하는 번호다. HTTP는 80, HTTPS는 443이 약속된 번호다.

IP 주소가 건물 주소라면 포트는 호실 번호다.

집이나 회사 안의 기기는 **사설 IP**(`192.168.…` 등)를 쓰고, 인터넷으로 나갈 때는 공유기가 **공인 IP**로 바꿔 준다. 이 일을 NAT라고 한다. 공유기는 어떤 기기가 어떤 포트로 보냈는지 장부를 적어 두고, 돌아온 응답을 맞는 기기에게 전한다. 클라이언트도 보낼 때 임시 포트를 하나 쓰기 때문에 가능한 일이다.

### 2-3. 패킷

데이터는 한 덩어리로 보내지 않고 작은 조각으로 잘라 보낸다. 조각 하나를 흔히 **패킷**이라고 부르고, 조각마다 보내는 곳과 받는 곳의 정보가 붙는다. 잘라 보내면 일부만 다시 보내면 되고, 여러 통신이 길을 나눠 쓸 수 있다.

대신 문제도 생긴다. 조각이 중간에 사라지거나 순서가 바뀔 수 있다. 인터넷의 기본 전달 방식(IP)은 도착을 보장하지 않는다.

### 2-4. TCP와 UDP

이 문제를 누가 처리할지에 따라 방식이 나뉜다.

| | TCP | UDP |
|---|---|---|
| 도착 보장 | 한다 (확인을 주고받고, 없으면 다시 보낸다) | 안 한다 |
| 순서 보장 | 한다 | 안 한다 |
| 시작 전 연결 | 필요하다 | 없다 |
| 쓰는 곳 | HTTP/1.1과 HTTP/2, 파일 전송 | 음성·영상 통화, DNS 조회, HTTP/3 |

사진 파일은 조각 하나만 없어도 깨지니 TCP가 맞다. 영상 통화에서는 뒤늦게 도착한 조각을 기다리는 것보다 건너뛰는 편이 낫기 때문에 UDP를 쓴다.

## 3. 요청이 가는 길

### 3-1. HTTP 요청 만들기

HTTP는 클라이언트와 서버가 쓰는 요청과 응답의 양식이다.

```
POST /messages HTTP/1.1                    ← 메서드와 경로
Host: api.example.com                      ← 헤더: 부가 정보
Content-Type: application/json
Authorization: Bearer (토큰)

{ "text": "안녕하세요" }                    ← 본문
```

- 메서드는 `GET`(가져오기), `POST`(만들기), `PUT`·`PATCH`(전체·일부 수정), `DELETE`(삭제)처럼 무엇을 할지 나타낸다.
- 응답의 상태 코드는 2xx(성공), 3xx(이동), 4xx(요청한 쪽 문제), 5xx(서버 문제)로 나뉜다.
- HTTP는 이전 요청을 기억하지 않는다(무상태). 그래서 로그인한 사용자라는 걸 요청마다 토큰이나 쿠키로 알려 준다.

### 3-2. URLSession이 해 주는 것과 내가 해야 하는 것

| 내가 정하는 것 | URLSession과 시스템이 해 주는 것 |
|---|---|
| URL, HTTP 메서드 | `Host`, `Content-Length` 같은 헤더 채우기 |
| 인증 헤더, `Content-Type` | 압축된 응답(gzip) 풀기 |
| 본문 만들기(JSON 인코딩) | 연결 맺기와 재사용 |
| 상태 코드 확인, 디코딩 | 쿠키, 캐시, 리다이렉트 처리 |

`Content-Length`, `Authorization`, `Connection`, `Host` 같은 헤더는 URL Loading System이 책임지는 **예약된 헤더**다. Apple 문서는 직접 설정하면 시스템이 무시하거나 덮어쓸 수 있으니 설정하지 말라고 안내한다. 다만 `Authorization`은 이 목록에 들어 있으면서도 토큰을 직접 넣는 코드가 흔하므로, 인증 방식을 설계할 때 문서의 이 주의를 알아 두는 편이 좋다.

주의할 점이 두 가지 있다.

**첫째, 본문의 인코딩은 내 몫이다.** `httpBody`에 넣는 `Data`는 직접 만들어야 하고, `Content-Type`도 직접 정해야 한다. 본문만 넣고 `Content-Type`을 생략하면 `application/x-www-form-urlencoded`가 붙어서, JSON을 보냈는데 서버가 폼 데이터로 해석할 수 있다.

```swift
var request = URLRequest(url: URL(string: "https://api.example.com/messages")!)
request.httpMethod = "POST"
request.setValue("application/json", forHTTPHeaderField: "Content-Type")
request.httpBody = try JSONEncoder().encode(["text": "안녕하세요"])
```

**둘째, 404나 500이 와도 에러가 던져지지 않는다.** 서버와의 통신 자체는 성공했기 때문이다. 상태 코드는 직접 확인해야 한다.

```swift
let (data, response) = try await URLSession.shared.data(for: request)

guard let http = response as? HTTPURLResponse,
      (200..<300).contains(http.statusCode) else {
    throw URLError(.badServerResponse)
}
```

### 3-3. DNS: 이름을 IP 주소로

네트워크는 `api.example.com` 같은 이름이 아니라 IP 주소로 움직인다. 이름을 주소로 바꿔 주는 것이 **DNS**다.

```
아이폰 → DNS 리졸버: "api.example.com 주소 알려 줘"
리졸버 → 루트 서버      : ".com 담당에게 물어봐"
리졸버 → .com 담당 서버 : "example.com 담당에게 물어봐"
리졸버 → example.com 담당: "203.0.113.10"
리졸버 → 아이폰: "203.0.113.10"
```

아이폰은 리졸버에게 한 번 묻고 답만 받는다. 리졸버의 주소는 Wi-Fi나 셀룰러에 접속할 때 미리 받아 둔다.

- 알아낸 답은 정해진 시간(**TTL**) 동안 저장해 둔다. 그래서 서버 주소를 바꿔도 한동안 예전 주소로 갈 수 있다.
- IPv4 주소를 알려 주는 기록은 **A**, IPv6 주소를 알려 주는 기록은 **AAAA**다.
- DNS는 URL 전체가 아니라 **도메인 이름 부분만** 바꾼다. `/users` 같은 경로는 연결한 뒤에 HTTP로 서버에 전달된다.
- DNS는 이름 조회를 위한 별개의 통신이다. HTTP 요청과 함께 가는 것이 아니라 먼저 다녀온다.

코드에 IP 주소를 직접 쓰지 말고 도메인을 써야 하는 이유도 여기에 있다. IP를 하드코딩하면 서버 주소가 바뀔 때 앱을 다시 배포해야 한다.

### 3-4. TCP 연결: 3-way handshake

IP 주소를 알았으면 데이터를 보내기 전에 연결부터 맺는다.

```
클라이언트 → 서버:  SYN       "연결하자"
서버 → 클라이언트:  SYN-ACK   "좋아, 나도 준비됐어"
클라이언트 → 서버:  ACK       "확인했어"
```

연결이 맺어지면 TCP는 조각에 순서 번호를 붙이고, 받았다는 확인을 주고받고, 없어진 조각은 다시 보내서 순서대로 맞춰 준다. 상대와 네트워크가 감당할 수 있도록 보내는 속도도 조절한다. 앱은 조각이 사라졌었는지도 알 필요가 없다. 다 쓴 연결은 종료 절차를 거쳐 닫는다.

다만 TCP의 확인은 상대 **컴퓨터까지** 도착했다는 뜻이다. 연결이 중간에 끊기면 서버 프로그램이 처리했는지는 알 수 없다. 그래서 채팅 앱 같은 곳에서는 "서버가 저장했다"는 응답을 앱끼리 따로 주고받는다.

### 3-5. TLS: 암호화 준비

TCP는 빠짐없이 전달할 뿐 내용은 그대로 노출된다. HTTPS에서는 TCP 연결 위에서 **TLS handshake**를 거쳐 상대가 진짜 서버인지 확인하고 암호화에 쓸 키를 만든다. 이 과정은 2편에서 자세히 본다.

### 3-6. 요청이 나가고 응답이 온다

이제야 준비해 둔 HTTP 요청이 암호화되어 나간다. 기기와 서버 사이를 한 번 왕복하는 시간을 **RTT**라고 하면, TLS 1.3 기준으로 첫 응답까지 대략 3번의 왕복이 필요하다(DNS 제외).

```
TCP handshake    1 RTT
TLS handshake    1 RTT
HTTP 요청·응답    1 RTT
```

## 4. 두 번째 요청은 왜 빠를까

### 4-1. Keep-Alive

응답을 받은 뒤 연결을 닫지 않고 다음 요청에 다시 쓰는 것을 **Keep-Alive**(지속 연결)라고 한다. HTTP/1.1부터 기본 동작이다.

```
첫 번째 요청 : DNS → TCP → TLS → HTTP
두 번째 요청 :                    HTTP
```

handshake를 반복하지 않으니 응답이 빠르고, 연결을 만드는 비용도 줄어든다. 물론 연결이 살아 있을 때의 이야기다. 오래 쓰지 않아 끊겼거나, 다른 호스트이거나, 네트워크가 바뀌면 새로 연결해야 한다.

### 4-2. iOS에서의 설정

따로 켤 것은 없다. URL Loading System이 지속 연결을 알아서 처리하고, `Connection` 헤더는 예약된 헤더라 직접 설정하지 않는다.

조절할 수 있는 것 중 하나는 `URLSessionConfiguration.httpMaximumConnectionsPerHost`다. 한 호스트에 동시에 맺는 **HTTP/1.1** 연결 수이고 기본값은 6이다. 세션 단위로 적용되며, HTTP/2 이상은 연결 하나에서 여러 요청을 동시에 처리하므로 이 값을 무시한다.

### 4-3. 세션을 재사용한다

개발자가 신경 쓸 것은 설정보다 **세션을 다시 쓰는 것**이다. 연결은 세션에 묶여 관리되어서, 요청마다 세션을 새로 만들면 이전 연결을 재사용하지 못한다.

```swift
// 피해야 할 방식: 요청마다 새 세션
func fetch(_ url: URL) async throws -> Data {
    let session = URLSession(configuration: .default)
    return try await session.data(from: url).0
}

// 권장: 세션 하나를 계속 사용
final class APIClient {
    private let session = URLSession(configuration: .default)

    func fetch(_ url: URL) async throws -> Data {
        try await session.data(from: url).0
    }
}
```

간단한 요청이라면 `URLSession.shared`를 계속 쓰면 된다.

## 5. 계층으로 묶어 보기

### 5-1. OSI 7계층과 TCP/IP 4계층

지금까지 본 것을 계층에 올려 보면 이렇다.

| TCP/IP | OSI | 하는 일 | 예 |
|---|---|---|---|
| 응용 | 7 응용 | 무슨 요청인지 정한다 | HTTP, DNS |
| | 6 표현 | 데이터 형식, 압축, 암호화 | JSON, gzip |
| | 5 세션 | 대화의 시작, 유지, 종료 관리 | |
| 전송 | 4 전송 | 빠짐없이 순서대로 전달 | TCP, UDP |
| 인터넷 | 3 네트워크 | 목적지까지 길 찾기 | IP |
| 링크 | 2 데이터 링크 | 바로 옆 장비까지 전달 | Wi-Fi, 셀룰러 |
| | 1 물리 | 신호 전송 | 전파 |

OSI 7계층은 설명용 모델이고 실제 인터넷은 TCP/IP 모델로 동작한다. 그래서 5, 6계층은 따로 구현되지 않고 응용 계층에서 함께 처리한다. TLS는 OSI에 딱 맞게 놓기 어려워서 전송 계층과 응용 계층 사이(5~6계층쯤)로 설명하곤 한다.

`URLSession`의 "Session"은 5계층을 뜻하지 않는다. 요청들을 묶어 관리하는 API의 이름이다. 로그인 세션이나 쿠키도 이름은 세션이지만 HTTP(7계층)에서 하는 일이다.

### 5-2. 계층은 순서가 아니라 역할이다

처음에는 계층을 "7번부터 1번까지 차례로 실행되는 단계"로 이해하기 쉽다. 계층은 **통신에 필요한 일을 역할별로 나눈 것**이다. 각 계층은 아래 계층에 일을 맡기고, 아래가 어떻게 처리하는지는 몰라도 된다. 덕분에 Wi-Fi에서 셀룰러로 바뀌어도 HTTP 코드는 고치지 않는다.

### 5-3. 번호는 "무엇이 있어야 무엇을 할 수 있나"다

계층 번호를 보고 "연결(4계층)이 세션(5계층)보다 먼저인데 왜 5가 위에 있지?"라는 의문이 들었다. 번호는 실행 순서가 아니라 **의존 관계**를 나타낸다. 연결이 있어야 그 위에서 대화를 관리할 수 있으니 4가 아래, 5가 위다.

그래서 두 가지 방향이 있다.

- **준비는 아래부터** 된다. 네트워크에 접속해 IP를 받고(1~3), 연결을 맺고(4), 암호화를 준비한다.
- **보낼 데이터는 위에서부터** 내려간다.

Wi-Fi 접속과 IP 할당은 앱이 요청하기 전에 이미 끝나 있다. DNS는 7계층 프로토콜이지만 TCP 연결보다 먼저 일어난다. 즉 전체 흐름이 계층 번호 순서대로 흘러가는 것은 아니다.

### 5-4. 데이터가 포장되는 과정

보내는 쪽은 위에서 아래로 내려가면서 각 계층의 정보를 덧붙이고(캡슐화), 받는 쪽은 아래에서 위로 올라가며 벗겨 낸다.

```
HTTP 요청
 → TLS로 암호화
   → TCP 헤더 추가: 포트, 순서 번호     (세그먼트)
     → IP 헤더 추가: 출발지·목적지 IP   (패킷)
       → Wi-Fi나 셀룰러 프레임          (프레임)
         → 전파                         (비트)
```

각 계층이 붙인 정보는 상대편의 같은 계층이 읽는다. TCP의 순서 번호는 서버의 TCP가 읽고, HTTP는 그런 것이 있었는지도 모른다.

## 정리

- `URLSession` 요청은 DNS 조회 → TCP 연결 → TLS → HTTP 순서로 진행되고, 연결이 살아 있으면 HTTP만 다시 보낸다.
- 본문 인코딩과 `Content-Type`, 상태 코드 확인은 내 몫이다.
- 연결은 세션에 묶여 있으니 세션을 재사용한다.
- 계층은 순서가 아니라 역할 분담이고, 번호는 의존 관계다.
- OSI의 5, 6계층은 실제 TCP/IP에서 응용 계층에 포함된다.

다음 편에서는 3-5에서 넘어간 TLS를 본다. 서버가 진짜인지 어떻게 확인하고, 암호화에 쓸 키를 어떻게 만드는지 다룬다.
