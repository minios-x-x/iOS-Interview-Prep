# App Store 심사 전에 챙길 것 ③ 스토어 페이지: 스크린샷, 메타데이터, 카피캣 (4/7)

[3편](https://velog.io/@jxxnnee/iOS-App-Store-심사-전에-챙길-것-심사-정보와-증빙-서류)에서는 심사팀에게 전달하는 정보를 다뤘다. 이번 편은 **사용자에게 보이는 쪽**, 즉 App Store 제품 페이지다. 스크린샷, 앱 이름, 설명 같은 메타데이터와 다른 앱을 베끼거나 사칭하는 것에 대한 규칙을 본다.

## 1. 스토어 페이지도 심사 대상이다

1편에서 심사 대상이 바이너리만이 아니라고 했다. 가이드라인 2.3 서두가 그 이유를 설명한다. 고객은 다운로드하거나 구입하려는 앱이 무엇인지 알아야 하므로, 개인정보 관련 정보를 포함한 **모든 앱 메타데이터, 앱 설명, 스크린샷, 미리보기**가 앱의 주요 경험을 정확히 반영해야 하고, **항상 최신 버전에 맞게 업데이트**해야 한다.

코드를 아무리 잘 만들어도 스토어 페이지가 앱과 다르면 리젝될 수 있다는 뜻이다.

## 2. 스크린샷 (2.3.3)

### 2-1. 규칙

가이드라인 2.3.3은 스크린샷에 **사용 중인 앱**이 보여야 한다고 한다. 제목 아트, 로그인 페이지, 스플래시 화면만 보여서는 안 된다. 텍스트나 이미지 오버레이(터치 포인트, Apple Pencil 같은 입력 방식 시연)와 Touch Bar 같은 기기의 확장 기능을 보여주는 것은 가능하다.

### 2-2. 과반 규칙

App Review Help의 [2.3.3 문서](https://developer.apple.com/help/app-review/guideline-reference/2-3-3-screenshots)는 이 규칙을 구체적인 기준으로 풀어 준다. 기기 종류별로 올린 스크린샷 세트에서 **절반을 초과하는** 수가 앱을 실제로 쓰는 화면이어야 승인된다.

| 올린 스크린샷 수 | 앱 사용 화면이 최소 몇 장이어야 하나 |
|---|---|
| 3장 | 2장 |
| 4장 | 3장 |

나머지 스크린샷은 마케팅 자료로 앱의 주요 장점과 기능을 보여줘도 된다. 스플래시나 마케팅 문구를 넣는 것도 과반이 앱 사용 화면이라면 괜찮다.

### 2-3. 해도 되는 것과 안 되는 것

| 해도 되는 것 | 하면 안 되는 것 |
|---|---|
| 기기별 스크린샷의 대부분을 주요 기능 화면으로 구성 | 일반적인 로그인 화면이나 스플래시만으로 구성 |
| 새 버전마다 현재 UI에 맞게 스크린샷 갱신 | 앱의 실제 인터페이스를 왜곡하거나 오해를 부르는 홍보물 사용 |
| 다크 모드 같은 다양한 구성을 포함 | 오버레이나 마케팅 이미지가 앱을 가려서 밀어냄 |
| 입력 방식을 보여주는 오버레이 | 앱 화면 없이 하드웨어나 오버레이만 보여줌 |
| 앱이 다른 Apple 플랫폼에서 도는 모습(경험의 일부일 때) | |

### 2-4. FAQ

- **기기마다 장수가 같아야 하나?** 아니다. 기기마다 달라도 되고, 앱 사용 모습을 보여주는 한 장이면 충분하다.
- **현지화별로 스크린샷이 달라도 되나?** 된다. 다만 각 현지화의 스크린샷도 과반이 앱 사용 화면인지 따로 평가된다.
- **앱 이미지 하나를 두 장 이상에 걸쳐 이어 붙여도 되나?** 된다.
- **상태 표시줄 등에 타사 플랫폼이 보이면?** 2.3.3이 아니라 가이드라인 2.3.10으로 평가된다.

## 3. 메타데이터 규칙 정리

가이드라인 2.3에는 스크린샷 외에도 규칙이 많다. 스크린샷을 제외한 항목을 번호순으로 정리하면 다음과 같다.

| 규칙 | 내용 |
|---|---|
| 2.3.1 | 새 기능과 변경 사항은 심사용 추가 정보에 구체적으로 설명한다. 실제로 제공하지 않는 콘텐츠나 서비스를 홍보하거나 허위 가격을 내세우면 앱 삭제와 개발자 계정 해지의 근거가 된다 |
| 2.3.2 | 앱 내 구입이 있으면 홍보하는 항목이 추가 구매를 필요로 하는지 설명, 스크린샷, 미리보기에 명확히 쓴다. 앱에서는 `SKPaymentTransactionObserver` 메서드를 올바르게 처리한다 |
| 2.3.4 | 미리보기는 앱 자체의 비디오 화면 캡처만 쓸 수 있다. 영상만으로 설명이 부족하면 내레이션이나 텍스트 오버레이를 추가할 수 있다 |
| 2.3.5 | 앱에 가장 적합한 카테고리를 고른다. 부적합하면 Apple이 바꿀 수 있다 |
| 2.3.6 | 연령 등급 질문에 정직하게 답한다. 잘못 지정하면 고객이 당황하거나 규제 당국의 조사를 받을 수 있다 |
| 2.3.7 | 앱 이름은 **30자 이내**이고 고유해야 한다. 이름, 부제, 스크린샷, 미리보기에 상표 용어, 인기 앱 이름, 가격 정보, 관련 없는 어구를 넣지 않는다. 부제는 부적절한 콘텐츠, 다른 앱에 대한 언급, 확인할 수 없는 제품 설명을 포함하지 않는다 |
| 2.3.8 | 아이콘, 스크린샷, 미리보기는 실제 앱 등급이 더 높아도 **4세 이상** 등급에 적합해야 한다. "어린이용" 같은 단어는 어린이 카테고리에서만 쓴다. 앱 이름과 아이콘은 서로 혼동되지 않게 비슷하게 맞춘다 |
| 2.3.9 | 아이콘, 스크린샷, 미리보기의 모든 자료에 대한 사용 권리를 확보한다. 실제 사용자 데이터 대신 **가상 계정 정보**를 표시한다 |
| 2.3.10 | 앱이 지원하는 Apple 플랫폼 경험에 집중한다. 특별히 승인된 기능이 없다면 앱이나 메타데이터에 다른 모바일 플랫폼이나 외부 앱 마켓플레이스의 이름, 아이콘, 이미지를 넣지 않는다 |
| 2.3.11 | 사전 주문으로 올리는 앱은 제출 시점에 완전하고 제공 가능한 상태여야 한다. 출시된 앱이 사전 주문 때 홍보한 앱과 실질적으로 달라서는 안 되고, 비즈니스 모델 변경 같은 중대한 변경이 있으면 사전 주문 판매를 다시 시작해야 한다 |
| 2.3.12 | 새 기능과 변경 사항은 "새로운 기능" 설명에 명확히 쓴다. 단순 버그 수정, 보안 업데이트, 성능 개선은 포괄적인 설명으로 충분하지만 중대한 변경은 기능을 명확히 나열해야 한다 |
| 2.3.13 | 앱 내 이벤트는 App Store Connect가 제공하는 이벤트 유형에 속해야 한다. 이벤트 메타데이터는 정확하고 그 이벤트와 관련 있어야 하며 앱의 일반 메타데이터를 쓰지 않는다. 이벤트는 정한 시간에 여러 스토어프론트에서 진행되어야 하고, 이벤트 딥 링크는 앱의 해당 위치로 연결되어야 한다 |
| 2.3.14 | 제품 페이지 헤더나 검색 결과 등에 쓰는 크리에이티브 애셋은 앱의 콘텐츠, 기능, 브랜드와 관련 있어야 하고 모든 대상에게 적합해야 한다. 부적절한 콘텐츠, 오도하는 다른 앱 언급, 확인할 수 없는 제품 설명, 구체적이거나 할인된 가격 정보는 넣지 않는다 |

모든 앱이 해당되는 규칙도 있고(2.3.5~2.3.9, 2.3.12), 사전 주문, 앱 내 이벤트, 크리에이티브 애셋처럼 그 기능을 쓸 때만 해당되는 규칙도 있다(2.3.11, 2.3.13, 2.3.14).

### 3-1. 규칙이 어떻게 적용되는지 보는 예

2.3.7의 문장을 가상의 앱 "북로그"에 적용해 보면 이렇다. 아래는 규칙을 이해하려고 내가 만든 예시이고, 실제 심사에서 이렇게 판정된다는 보장은 없다.

| 항목 | 규칙에 어긋나 보이는 예 | 규칙에 맞는 예 |
|---|---|---|
| 앱 이름 | `북로그 - 최저가 무료 독서 앱` (가격 정보를 이름에 넣음) | `북로그` |
| 부제 | `세계 1위 독서 앱` (확인할 수 없는 제품 설명) | `읽은 책을 기록하고 통계로 확인` |
| 키워드 | 유명 독서 앱 이름을 키워드로 넣음 | 앱 기능을 설명하는 단어 |

2.3.9는 스크린샷을 찍을 때 특히 신경 쓰인다. 개발 중에 실제 계정으로 로그인한 상태에서 캡처하면 이름이나 이메일이 화면에 보일 수 있다. 스크린샷용 데이터는 가상의 계정으로 따로 만들어 두는 편이 안전하다.

## 4. 카피캣과 사칭 (4.1)

### 4-1. 가이드라인 4.1

가이드라인 4.1은 세 가지를 다룬다.

- **(a) 본인의 아이디어로 만든다.** 인기 앱을 모방하거나 다른 앱의 이름이나 UI를 조금 바꿔서 내면 안 된다. 지식재산권 침해 소송의 위험도 있고, App Store 탐색을 어렵게 하며, 다른 개발자에게 공정하지 않다고 설명한다.
- **(b) 다른 앱이나 서비스를 사칭하지 않는다.** 사칭은 개발자 행동 수칙 위반이고, Apple Developer Program에서 제명될 수 있다.
- **(c) 다른 개발자의 아이콘, 브랜드, 제품 이름을 내 앱의 아이콘이나 이름에 쓰려면 그 개발자의 승인이 필요하다.**

### 4-2. Help 문서의 해설

[4.1 문서](https://developer.apple.com/help/app-review/guideline-reference/4-1-prevent-copycat-rejection)는 이 규칙을 세 가지 실천 사항으로 나눈다.

| 실천 사항 | 해야 할 것 | 하지 말 것 |
|---|---|---|
| 고유한 콘텐츠와 기능 | 새로운 경험이나 기존 개념의 독창적인 해석, 독창적인 인터페이스 | 다른 앱의 기능이나 룩앤필을 모방 |
| 정확하고 관련 있는 메타데이터 | 설명적인 언어, 독창적인 콘텐츠, 실제 앱 사용 화면 스크린샷 | 허가 없이 보호받는 자료 사용, **어느 메타데이터 칸에도** 유명 앱 이름이나 상표 포함 |
| 진짜이고 검증 가능한 정보 | 개발자나 회사 이름, Support URL 같은 계정과 앱 정보를 최신으로 유지 | 오래된 지원 페이지로 연결하는 등 부정확한 정보, 위조 서류 제출 |

결과도 분명하다. 카피캣 앱은 리젝되고, **카피캣을 반복해서 내거나 서비스를 사칭하면 계정이 닫힌다.** 위조 서류를 낸 계정은 Developer Program에서 제거된다.

### 4-3. 2.3.7과의 관계

4.1과 2.3.7은 같은 주제를 다른 각도에서 다룬다. 4.1은 앱 자체를 베끼지 말라는 규칙이고, 2.3.7은 메타데이터에 남의 이름이나 상표를 끼워 넣지 말라는 규칙이다. 앱을 아무리 독창적으로 만들어도 검색 노출을 위해 인기 앱 이름을 키워드에 넣으면 걸릴 수 있다.

## 정리

- 메타데이터, 스크린샷, 미리보기는 앱의 주요 경험을 정확히 반영해야 하고, 새 버전에 맞게 최신으로 유지해야 한다.
- 스크린샷은 기기별 세트의 **과반이 앱을 쓰는 화면**이어야 한다. 로그인이나 스플래시만으로는 안 된다.
- 앱 이름은 30자 이내이고, 이름, 부제, 스크린샷, 미리보기에 가격이나 남의 상표, 확인할 수 없는 설명을 넣지 않는다.
- 스크린샷에는 실제 사용자 데이터 대신 가상 계정 정보를 쓴다.
- 카피캣이나 사칭은 리젝을 넘어 계정 해지까지 이어질 수 있다.

### 제출 전 스토어 페이지 점검표

- [ ] 기기별 스크린샷의 절반을 넘는 수가 앱 사용 화면인가
- [ ] 스크린샷이 현재 버전의 UI와 일치하는가
- [ ] 스크린샷에 실제 사용자 이름이나 이메일이 보이지 않는가
- [ ] 앱 이름이 30자 이내이고 가격이나 남의 상표가 없는가
- [ ] 부제와 키워드에 다른 앱 이름이나 확인할 수 없는 홍보 문구가 없는가
- [ ] 아이콘, 스크린샷, 미리보기가 4세 이상 등급에 적합한가
- [ ] 앱 내 구입이 있다면 추가 구매 여부를 설명과 스크린샷에 명시했는가
- [ ] 연령 등급 질문에 정직하게 답했는가
- [ ] "새로운 기능" 설명이 이번 변경을 반영하는가
- [ ] 개발자 이름, Support URL이 정확하고 최신인가

다음 편에서는 앱 안으로 들어간다. 권한과 개인정보 관련 규칙(5.1.1)과 목적 문구, 현지화, SDK 책임을 다룬다.
